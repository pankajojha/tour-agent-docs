01 — Overview

What this platform is, and how far it's gotten

Travelers assemble a trip — shore excursions, hotels, flights, cruise legs, dining — inside tour-planner-ui. tour-agent is the system of record for every transactional fact (users, trips, bookings, policy). tour-planner-ai is a stateless Bedrock AgentCore orchestrator that reasons over redacted trip data and is never allowed to own state directly. tour-commerce sits on top as the cart/checkout/payments layer, calling both of the above before a booking is ever created. A Strapi CMS was modeled in parallel but isn't wired in yet.

02 — System Map

Service boundaries and data flow

Everything client-facing enters through tour-agent. Sensitive fields are sanitized before any AI call. tour-planner-ai only ever sees redacted payloads and never touches either database directly for user-facing writes. The CMS sits outside this flow entirely today.

Dashed edges mark links that are documented but not exercised by any caller in the codebase today.

  1. 01
    tour-planner-ai never owns transactional state — it reads via MCP tools and writes go through tour-agent APIs. (Currently unmet: writes go to the mock API, not tour-agent — see Gap Analysis.)
  2. 02
    One active trip per user, enforced by a DB unique index plus an application-layer 409.
  3. 03
    Privacy first — every text payload passes through prepare_model_input() before reaching the model; no PII/PCI is sent to Bedrock.
  4. 04
    Strict AI-proxy allowlist — ai-proxy forwards only ~11 named routes; there is no wildcard path.
  5. 05
    Trip lifecycle is data-driven — trip_status_transitions and trip_operation_rules own the FSM; the UI reads /operations and /ui-hints rather than hardcoding status logic.
  6. 06
    Privilege escalation is blocked — the policy service checks the caller's role level before allowing any role assignment.

What's real, what's a stub

Each workspace below was read directly — service by service — rather than taken on faith from its own README.

04 — Data & Security

Schema and the security model

Two independent Aurora Serverless v2 clusters — deliberately not shared — plus the controls layered around them.

tour-agent database — 4 migrations

MigrationContents
V001Core: AppUsers, social_profiles, sessions, destinations, categories, suppliers, excursions, schedules, bookings, payments, reviews, inventory, pricing
V002AI & collaboration: ai_runs, webhooks, trip_plans, trip_category_entries, contributor blocks, trip_status_transitions, trip_operation_rules, trip_ui_hints
V003Policy: 5-tier RBAC (roles, user_roles), company_policies, policy_rules, policy_evaluations, policy_overrides, approval workflow
V004Prompts: system_prompts, system_prompt_activations, activate_system_prompt(), active_system_prompts view, RLS

Trip lifecycle FSM: draft → active → shared → finalized → consumed, transitions data-driven from trip_status_transitions. One active trip per owner enforced by uq_one_active_trip_per_owner. RBAC tiers, highest privilege first: platform_admin(1) → company_admin(2) → travel_manager(3) → dept_manager(4) → traveler(5).

tour-commerce database — 1 migration, separate cluster

commerce_carts / commerce_cart_items · commerce_checkout_sessions (short-lived, carries an AI validation snapshot) · commerce_orders / commerce_order_items (linked back via tour_agent_booking_id) · commerce_payments (Stripe) · commerce_ai_interactions (audit log of every AI call made during commerce).

06 — Project Plan

Sequencing the work to completion

Four phases, ordered by blast radius first, then by what unlocks the next phase. Aspirational-spec items (WAF, OpenSearch, DR, notifications) are deliberately last — they're additive, not blocking, for an MVP launch.

Phase 0

Stop the bleeding

1–2 weeks

Fix the tour-commerce deploy-blocking asset reference; replace the Stripe placeholder secret with a real rotation step; delete the dead auth-stack.ts and the stale terraform/ spike; resolve the app-user/tour-user Strapi collision.

Phase 1

Close the MVP loop

4–8 weeks

Wire tour-planner-ai's MCP tools to real tour-agent endpoints instead of the mock API. Finish the 3 stubbed agents. Build the missing UI surfaces: trip dashboard, an AI chat/assistant page, and a minimal admin view for policy. Replace the mock purchase flow with the real search/quote calls that already exist.

Phase 2

Make it safe to change

4–6 weeks

Add test coverage to tour-agent, tour-commerce, and tour-planner-ai — property tests for inventory/booking atomicity and pricing were explicitly planned but never written. Stand up real CloudWatch alarms/SNS/dashboards. Wire a CI/CD pipeline for tour-planner-ui. Decide the CMS's fate: integrate it as the excursion/content authoring surface, or retire it.

Phase 3

Aspirational-spec backlog

Ongoing, post-launch

Voucher generation with QR check-in, reviews & ratings, the recommendation engine, OpenSearch-backed search/facets, WAF, multi-region DR, notification system (SES/Pinpoint), audit-log query UI. Pull items forward only as real usage demands them.

Sequencing rationale: Phase 0 items are each under a day of work but currently block a clean deploy or create silent risk — fix them before anything else lands on top. Phase 1 is what turns "impressive demo" into "a trip you could actually book end to end." Phase 2 is what makes Phase 1's code trustworthy to keep changing. Phase 3 is the difference between an MVP and the original 39-task aspirational spec — most of it shouldn't be built until real usage says which pieces matter.
07 — Ops Addendum · 30 Jul 2026

Findings since the survey

Operational discoveries made after the 26 Jul survey, while diagnosing and fixing a production login outage on exploreragents.com/auth. These are facts about the deployed system that no design doc records.

StatusFindingDetail
Fixed Login outage: UI built against a deleted API Gateway tour-planner-ui/.env pointed VITE_AUTH_BASE_URL at gateway 4q8rnlwz6l, which no longer exists (NXDOMAIN at the authoritative DNS). The live gateway is 5dny4g2ebl (explorer-agent-api, created 18 Apr 2026, stages dev + production). Fixed, rebuilt, redeployed, verified end-to-end against real Cognito responses. The same stale ID was also fixed in both Postman environment files.
Trap Cloudflare Pages project mismatch exploreragents.com is served by the Pages project named exploreragents — not tour-planner-ui, which the root Readme.md deploy command targets. Deploying to tour-planner-ui publishes only to tour-planner-ui.pages.dev and never touches the live domain. Any deploy instructions or CI pipeline must target exploreragents.
Open Trips and policy APIs still point at the dead gateway VITE_TRIPS_API_URL and VITE_POLICY_API_URL in tour-planner-ui/.env still reference 4q8rnlwz6l. The live gateway only exposes /auth/* and /v1/{excursions,destinations,bookings} — no trips or policy routes were found on it, so trip-lifecycle and policy features on the live site are presumed broken until their real endpoints are located or redeployed.
Note Wrangler v4 requires Node ≥ 22 The pinned wrangler@^4.94.0 refuses to run on the deploy host's Node v20. Deploys currently use npx wrangler@3 as a workaround; either upgrade Node on the host or pin wrangler v3 deliberately.
Added Monorepo docs site A root-level Dockerfile + generate.py render every Markdown file across all six workspaces (45 files) into a themed, navigable static site served by nginx (docker compose up --build, port 8088 — currently running on port 80 on the dev host). tour-agent-docs was regrouped into business-model/ and fundraising/, with cross-doc links repaired.
Pattern worth naming: both the login outage and the Pages mismatch are the same failure class — infrastructure was recreated or renamed, and the identifiers baked into config files and docs silently went stale. Nothing in the codebase derives these values from the source of truth (CloudFormation outputs, Cloudflare project bindings). A small post-deploy script that writes .env from stack outputs would eliminate the class.
